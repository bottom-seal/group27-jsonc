# Boundary state, not bytes, breeds json-c bugs

Every bug class in the published JSON-parser literature has a json-c counterpart, and the team's harnesses already test almost all of them. That holds for the interoperability classes (duplicate keys, keys that collide after a character is dropped, comments that hide members, number overflow, BOM, NUL, lone surrogates, depth, trailing garbage) and for the streaming classes (state lost across chunks, limits checked only when a token completes, over-reads on truncated input). json-c's own record points where the team's eight findings landed. **Only four CVEs actually belong to json-c**, and both CVE families that touch parsing needed a second fix years after the first. More than 45 tokener and buffer fixes fall into six root-cause families, and the two largest are per-call state lost across chunk boundaries and the shared `out:` epilogue (the exit code every parse path runs through) overwriting errors. The one peer-reviewed differential study that included json-c (Crossy, AsiaCCS 2024) found **zero value differences between json-c and seven other parsers**, and JSONTestSuite's json-c column comes from json-c 0.12 (2014) run through a flawed harness. This round's checks (flag monotonicity, escape equivalence, exact-size heap chunks with no terminating NUL, MemorySanitizer, the decimal-comma locale and the exhaustive number alphabet) were all clean. What remains uncovered is narrow: error-code consistency across flag sets, hash flooding, memory amplification, OOM injection in split and stream modes, BOM handling, key collisions caused by surrogate replacement, 32-bit builds, and continuous upstream fuzzing of the incremental API. Two "2026 CVEs" named in json-c's 0.19 ChangeLog do not check out and should not be cited as json-c vulnerabilities.

## Every published bug class has a json-c analogue, and most are already fenced

Interoperability bugs come from two parsers reading the same bytes differently, and the classic exploit uses a duplicate key. In Apache CouchDB's **CVE-2017-12635**, the JavaScript and Erlang parsers disagreed about which of two `roles` keys won, and the result was privilege escalation to remote code execution ([Seriot](https://seriot.ch/projects/parsing_json.html)). Bishop Fox surveyed 49 parsers and found seven, RapidJSON among them, that keep the first value of a duplicate key. Some DOMs keep both members and serialize a different one from the one a lookup returns. A subtler family makes two *different* keys collapse into one after the parser drops or rewrites a character: a lone surrogate (`"test\ud800"` in ujson), a backslash before a raw CR, a stray quote, or an invalid escape such as `\s` that is silently dropped ([Bishop Fox](https://bishopfox.com/blog/json-interoperability-vulnerabilities)). ujson's **CVE-2022-31116** is that collision: unpaired surrogates were decoded wrongly, so dictionary keys collided and values were overwritten ([OSV](https://osv.dev/vulnerability/CVE-2022-31116)). Neither Bishop Fox nor Seriot's article tested json-c.

In json-c, a later duplicate replaces the earlier value (last wins). Keys are stored as `strdup`'d C strings, so a key containing `\u0000` is cut at the NUL and `{"a\u0000b":1,"a":2}` becomes `{"a":2}`. That case is already known as #715 and PR #1007 ([json_tokener.c](https://github.com/json-c/json-c/blob/master/json_tokener.c); [linkhash.c](https://github.com/json-c/json-c/blob/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/linkhash.c#L491)). Lone surrogates become U+FFFD, which has a consequence nobody has tested: `{"a\ud800":1,"a\udc00":2}` should collapse into a single member, exactly the way ujson's keys did.

Numbers diverge the most. A 96-digit run of 9s decodes as `9.999999999999999e95`, `1E+96`, `0` or INT64_MAX depending on the parser, and Go's jsonparser turns `1.0e4096` into 0 without an error ([Bishop Fox](https://bishopfox.com/blog/json-interoperability-vulnerabilities)). cJSON turns `10000000000000000999` into `10000000000000002048` ([Seriot](https://seriot.ch/projects/parsing_json.html)). json-c's STRICT mode rejects integer overflow with ERANGE but, as the team observed, silently turns `1e400` into infinity.

The BOM is a differential the spec itself allows. RFC 8259 says parsers MAY ignore one, and an erratum asking to let a BOM signal an alternate encoding was rejected ([RFC Errata 6208](https://www.rfc-editor.org/errata/eid6208)). The only json-c data point is JSONTestSuite's 0.12 run, which rejected `i_structure_UTF-8_BOM_empty_object` ([logs.txt](https://github.com/nst/JSONTestSuite/blob/master/results/logs.txt)). No source documents what current json-c does.

Depth was the main crash class in Seriot's study: cJSON, ccan, JSONKit and SBJSON crash on deep nesting, and JSON.sh segfaults on 100,000 `[` ([Seriot](https://seriot.ch/projects/parsing_json.html)). jackson-databind's CVE-2020-36518 is the Java version ([OSV](https://osv.dev/CVE-2020-36518)), and Go added a 10,000-level limit to its decoder ([Go commit 84afaa9](https://go.googlesource.com/go/+/84afaa9e9491d76ea43d7125b336030a0a2a902d)). Trailing garbage after a valid value enables form-based CSRF, because `{"test": 1}=` sent as urlencoded form data still parses as JSON ([Bishop Fox](https://bishopfox.com/blog/json-interoperability-vulnerabilities)). Go's `Decoder.Decode` accepts trailing data that `Unmarshal` rejects ([Trail of Bits](https://blog.trailofbits.com/2025/06/17/unexpected-security-footguns-in-gos-parsers/)).

Streaming parsers add classes that a whole-buffer parser cannot have. The clearest is a **limit enforced only when a token completes**. Jackson's non-blocking parser skipped its `maxNumberLength` check (GHSA-72hv-8253-57qq), and the first fix missed the integer-digit path ([OSV](https://api.osv.dev/v1/vulns/GHSA-72hv-8253-57qq)). A proof of concept then fed 16 KiB of digits 600 times and had about **9.83 MB accepted against a 1,000-digit limit** before any terminator arrived ([SecureLayer7](https://securelayer7.net/lab/jackson-core-async-parser-maxnumberlength-bypass-chunked-digits); [GHSA-r7wm-3cxj-wff9](https://github.com/FasterXML/jackson-core/security/advisories/GHSA-r7wm-3cxj-wff9)). json-c avoids this shape because its checks for control characters, UTF-8, depth and literals run per byte. The flip side is that it has no per-token length limit at all. Token memory is bounded only by printbuf's INT_MAX cap, which the team's Finding 7 already demonstrated for comments.

The remaining streaming classes all have external precedents. jsmn loses container state across calls ([jsmn #183](https://www.github.com/zserge/jsmn/issues/183)). The `jsonparse` and `clarinet` JavaScript parsers turned a multibyte character split across chunks into U+FFFD ([demo](https://github.com/jlank/streaming-jsonparsers-utf8-bug-demo)); json-c's version is PR #1014. Truncated input causes one-byte over-reads: simdjson's CVE-2026-88358 reads `buf[len]` when a truncated document ends by closing a nested container ([Red Hat](https://bugzilla.redhat.com/show_bug.cgi?id=2543058)), and cJSON's CVE-2023-53154 over-reads on `{"1":1,` ([OSV](https://osv.dev/vulnerability/CVE-2023-53154)). Go shipped a wrong-offset-after-EOF regression ([Go commit 7ecf1df](https://go.googlesource.com/go/+/7ecf1dff692a62278bdecc8e1223455fcff66ec9)), and a Jackson wrapper looped forever on "need more input" ([jackson-core #1144](https://github.com/FasterXML/jackson-core/issues/1144)).

Lenient extensions fail in recognizable ways. jsoncpp treated a comment followed by any token other than `}` as a comma ([jsoncpp 0a9b9d9](https://pigweed.googlesource.com/third_party/github/open-source-parsers/jsoncpp/+/0a9b9d9c6ea04847af83c32930176ec42ba6c842)). RapidJSON parsed `NaN.2e2` as 20 because it kept consuming number syntax after the literal ([RapidJSON 7c73dd7](https://gitlab.cristal.univ-lille.fr/pirvi-public/rapidjson/-/commit/7c73dd7de7c4f14379b781418c6e947ad464c818)). jsmn's non-strict recovery let a string token acquire children, so a consumer read past the token array (CVE-2026-95117 and CVE-2026-88369) ([jsmn #249](https://github.com/zserge/jsmn/issues/249)). The table maps each class to json-c and to the team's coverage.

## Four real CVEs, two phantom ones, and a habit of half-fixes

OpenCVE and Debian's tracker agree that json-c has exactly **four CVEs**, all resolved ([OpenCVE](https://app.opencve.io/cve/?product=json-c&vendor=json-c); [Debian](https://security-tracker.debian.org/tracker/source-package/json-c)). Florian Weimer reported the first two together in 2014. CVE-2013-6371 was a hash-collision denial of service, in which a weak string hash made parsing small crafted objects take quadratic time; 0.12 fixed it with a seeded hash ([oss-security](https://openwall.com/lists/oss-security/2014/04/09/9)).

CVE-2013-6370 was printbuf's use of `int` lengths, but its fix never touched `printbuf.c`. It only rejected a single call whose `len` exceeds INT32_MAX ([64e3690](https://github.com/json-c/json-c/commit/64e36901a0614bf64a19bc3396469c66dcd0b015)), which did nothing about growth across calls. **Six years later the same overflow came back, reached cumulatively, as CVE-2020-12762**, an out-of-bounds write through `printbuf_memappend` on a large file ([d07b910](https://github.com/json-c/json-c/commit/d07b91014986900a3a75f306d302e13e005e9d67)). That fix added INT_MAX guards to printbuf and linkhash, and it shipped a backwards comparison that capped objects at 11 keys until a follow-up six days later ([519dfe1](https://github.com/json-c/json-c/commit/519dfe1591d85432986f9762d41d1a883198c157)).

CVE-2021-32292, rated CVSS 9.8, was a stack overflow in the `apps/json_parse` sample tool caused by unbounded arithmetic on `json_tokener_get_parse_end()` ([4e9e44e](https://github.com/json-c/json-c/commit/4e9e44e5258dee7654f74948b0dd5da39c28beec)). Its fix bounded the read by buffer capacity rather than by bytes actually read, and issue #929 reopened it in 2026 as an information disclosure ([1d65898](https://github.com/json-c/json-c/commit/1d658982e591389341a92aae2ee54cd26e81beb5)). Both `apps/json_parse` bugs are callers misusing the parse-end contract, which counts from the start of the last call and is not cumulative. The team's observation about the header's own example shows how easy that contract is to get wrong.

Three CVE references need caution. The 0.19 ChangeLog attaches **CVE-2026-11322** to issue #929, but the public record (published by VulnCheck on 2026-06-04) describes a Hermes WebUI symlink path traversal, and only an openSUSE advisory links the ID to json-c ([GCVE](https://db.gcve.eu/vuln/cve-2026-11322)). The research notes disagree with each other on it: one set lists it as a json-c information disclosure on the strength of the ChangeLog alone. **CVE-2026-9146**, which the ChangeLog ties to a documentation change about iterator invalidation, has been rejected by its CNA ([SUSE](https://suse.com/security/cve/CVE-2026-9146)). Neither 2026 ID is parser-related, and both are best treated as mis-cited. Outside json-c, jansson's **CVE-2020-36325** (a non-NUL-terminated buffer passed to a NUL-terminated API) was closed as NOTABUG by Red Hat and may yet be rejected ([Red Hat](https://bugzilla.redhat.com/show_bug.cgi?id=1954173)). The notes also give two fix commits for CVE-2020-12762: 9021cdc (from OSV) and d07b910 (read in a clone, PR #592). These are probably the merge commit and the content commit.

Beyond the CVEs, more than 45 parser and buffer fixes fall into six root-cause families ([ChangeLog](https://github.com/json-c/json-c/blob/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/ChangeLog)). **State lost across chunk boundaries** is the densest, and the `\u` escape and surrogate code is its centre, with at least five fixes between 2020 and 2026. PR #633 (issue #616, surrogate pairs split across chunks) introduced a global-buffer-overflow that OSS-Fuzz caught the next day ([36118b6](https://github.com/json-c/json-c/commit/36118b681ea3b8e99735beee73cbd25a63e942cd)), and the proper fix moved surrogate handling into extra tokener states ([a68566b](https://github.com/json-c/json-c/commit/a68566bf6a2b44b5932072e85261a971097bc0a9)). PR #893 widened a 16-bit surrogate mask that misclassified decoded supplementary code points such as U+1D800 ([2372e95](https://github.com/json-c/json-c/commit/2372e9518e6ba95b48d37ec162bc7d93b297b52f)). Issue #984 found that `json_tokener_reset()` left a pending high surrogate that could combine with the next document ([7662139](https://github.com/json-c/json-c/commit/7662139501603434eba79aa7b916d1497d3d9cf4)). Numbers are the family's second hotspot: `-` and `Infinity` split across calls ([48f7e38](https://github.com/json-c/json-c/commit/48f7e389fb90c3647d0c846694a9456a7bf8ca3f)), exponents split across calls ([6eac698](https://github.com/json-c/json-c/commit/6eac6986c9a734b183e55a80e84fa67e58c637ff)), and today's open PR #1006.

The **`out:` epilogue** family comes from three unconditional rewrites at the shared exit: the pending-UTF-8 check, the strict trailing-character check, and the rewrite to `parse_eof` once the NUL has been seen ([json_tokener.c#L1389-L1406](https://github.com/json-c/json-c/blob/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/json_tokener.c#L1389-L1406)). Commit 99c14de (November 2026) worked around the EOF rewrite only at the two ERANGE call sites and left the epilogue itself alone ([99c14de](https://github.com/json-c/json-c/commit/99c14deceb959ee399018c74372250b2ce71f946)). That is why the team's Finding 5 and its strict-number-at-EOF observation still reproduce.

The **OOM and ownership** family has run for a decade. A 2016 change returned NULL with `success` when an allocation failed ([77a4276](https://github.com/json-c/json-c/commit/77a4276a8c210e1faa2e8c13421e9a3d62772340)). Later fixes addressed a use-after-free on the allocation-failure path of `json_tokener_new_ex` ([9361d8d](https://github.com/json-c/json-c/commit/9361d8d3a89475f5aadcac2c5473da1c4c47c7e2)) and values silently truncated on OOM ([9e6acc9](https://github.com/json-c/json-c/commit/9e6acc9a4eefe9f092aa3a3890a6e5c6ca2d5ed1)). In 2026, fault injection across 469 injection points found a leaked value when insertion into the parent fails ([e0a1735](https://github.com/json-c/json-c/commit/e0a173518f20640511def9842cea33183ddfe992)).

The other three families are smaller. **Signed char and int lengths** covers issues #407, #645 and #875, plus the CVE chain above; #875 was a strict control-character check that rejected every byte at or above 0x80 ([565f181](https://github.com/json-c/json-c/commit/565f181f656439847ef79650caad5c0b6c20171b)). **Locale lifecycle** has had six rounds of fixes, the latest of which, fd92d58, created the static locale behind the team's Finding 8 ([fd92d58](https://github.com/json-c/json-c/commit/fd92d58f2d2392aae2ec32d482871042531d0964)). **Strict-mode gaps** have been closed one at a time: control characters (#867), then keys, then leading zeros ([ff18c75](https://github.com/json-c/json-c/commit/ff18c75286d92045d37702e3ea59fea6b97241de)), then the full RFC number grammar ([e222189](https://github.com/json-c/json-c/commit/e222189360ff5a6201d42582a0fe15abc9d4cc11)).

For a bug hunter, the key pattern is that **at least nine fixes needed a follow-up fix**, from the 2013 bound on `json_tokener_error_desc()` to 99c14de's partial ERANGE patch. A fix at one call site leaves the variants behind it, so the team's reports will be stronger if they propose fixes at the epilogue or at the root cause rather than where the reproducer happens to land. The strict-mode history also predicts the next item: STRICT still accepts `[NaN]`, `[Infinity]` and `[-Infinity]`, although its documentation warns that it "may become more restrictive from one release to the next" ([json_tokener.h#L144-L159](https://github.com/json-c/json-c/blob/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/json_tokener.h#L144-L159)). The team logged this as a documented difference, and given the history it is better filed as the next conformance tightening than as a bug.

printbuf has its own lineage. In 2012 came an off-by-one in `printbuf_memappend` and wrong size arithmetic in `printbuf_memset` ([0d79b53](https://github.com/json-c/json-c/commit/0d79b534568f609a9444c3466ae1f5a2864f702f)). Negative lengths and totals above INT_MAX were rejected from 2022 ([4355242](https://github.com/json-c/json-c/commit/435524247782e8fc64a96e9e18e7d1bfecbb9dd0)). In 2026, a self-append use-after-free occurred when the source pointed into `p->buf` and `realloc` moved it ([62bb838](https://github.com/json-c/json-c/commit/62bb838c5734b863872c7c9ed4a8b6cbdb280714)), and `printbuf_memset` was found leaving `buf[bpos]` unterminated ([b5cd62d](https://github.com/json-c/json-c/commit/b5cd62dcad3b5fbd5e33276f99073e1ff80a6a3a)). One gap remains, reachable only through the public API. The `printbuf_memappend_fast` macro still uses `memcpy` although the header now promises overlap safety, and its guard lets a negative size through to `memcpy` as a huge `size_t`. Open PR #1011 turns the macro into an inline function but keeps both problems ([printbuf.h#L48-L73](https://github.com/json-c/json-c/blob/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/printbuf.h#L48-L73)). The tokener no longer calls it, and the issue comes from reading the code, not from a test.

OSS-Fuzz has one public json-c finding, OSV-2020-252: the PR #633 overflow, fixed within a day ([OSV](https://osv.dev/vulnerability/OSV-2020-252)). The 2026 bugs came from people, fault injection and review rather than OSS-Fuzz, and the harness explains why. `tokener_parse_ex_fuzzer.cc` makes **one default-flag `json_tokener_parse_ex` call with no terminating NUL** ([fuzz/](https://github.com/json-c/json-c/tree/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/fuzz)). It never chunks the input, never sets STRICT or VALIDATE_UTF8, and never resets or reuses a tokener. It reaches the EOF epilogue only when an input happens to contain a raw 0x00. Its 21-token dictionary has no `\u` escapes, no `/*` and no multibyte UTF-8. OSS-Fuzz builds the project for x86_64 and i386 and runs libFuzzer, AFL and honggfuzz with ASan and UBSan, but not MSan or TSan ([oss-fuzz projects/json-c](https://github.com/google/oss-fuzz/tree/master/projects/json-c)).

## Differential studies find json-c unremarkable, which moves the hunt off value semantics

Seriot's "Parsing JSON is a Minefield" ran more than 30 parsers against more than 300 handcrafted and AFL-derived files and found no two that behaved alike, with crashes clustered on deep nesting and invalid UTF-8 ([Seriot](https://seriot.ch/projects/parsing_json.html)). The article never mentions json-c. The JSONTestSuite repository does run json-c, but its setup script checks out **json-c-0.12** ([get_json-c.sh](https://github.com/nst/JSONTestSuite/blob/master/parsers/test_json-c/get_json-c.sh)). Its harness calls `json_tokener_parse_ex(tok, data, strlen(data))` once. It never reads the error code, never compares the parse end with the length, truncates input at an embedded NUL, and frees a buffer that the object owns ([main.c](https://github.com/nst/JSONTestSuite/blob/master/parsers/test_json-c/test_json-c/main.c)).

The published json-c column shows 52 should-have-failed, 5 should-have-passed, 30 implementation-defined (i_) files accepted, 5 rejected, and no crashes ([logs.txt](https://github.com/nst/JSONTestSuite/blob/master/results/logs.txt)). Most of that is harness artefact. The five false rejections are top-level scalars that end exactly at the buffer end, which json-c's documented rule ("the length passed MUST include the final '\0'") explains ([json_tokener.h](https://github.com/json-c/json-c/blob/master/json_tokener.h)). Most false acceptances are trailing garbage the harness never checked for. The team's strict-mode run supersedes this column. The i_ files are still useful as a checklist of implementation-defined dimensions (integer range, double overflow, UTF-8 validation, BOM, UTF-16 and depth), but those need oracles that check the resulting value, not just accept or reject.

**Crossy** (AsiaCCS 2024) is the only peer-reviewed study that included json-c. It fuzzed 22 parsers in C, C++, Rust, Java and Python with libFuzzer feeding one shared coverage map, normalized the outputs through a consensus ensemble, and compared the resulting trees node by node, over 24 hours on 96 instances. It found 29,266 unique inputs that made parsers disagree, among them large numbers dropped by cJSON, jansson and poco, strings truncated at U+0000, and frozen's mangled member names (CVE-2023-48891). It reported no crashes ([Crossy PDF](https://www.mlsec.tu-berlin.de/docs/2024b-asiaccs.pdf)). json-c had **zero differences with jansson, jsmn, libjson, yajl, jsoncpp, nlohmann and jackson**, and two to five with most of the others. It was flagged only for accepting raw control characters, which is its documented lenient default.

The implication is direct: under default flags and one-shot feeding, json-c's value semantics match the mainstream, and another broad cross-parser differential is unlikely to find more. Crossy compared strings code unit by code unit, so json-c's NUL-key truncation would have shown up only if a generated key contained `\u0000`.

The other studies did not test json-c, but they set expectations. Gmutator (TOSEM 2025) mutates the grammar itself to generate near-valid inputs. It produced thousands of accept-invalid inputs for cJSON and Parson and none for simdjson, and Parson's maintainers rejected the `[true, ]` and `{} {}` reports under the robustness principle ([TOSEM PDF](https://www.doc.ic.ac.uk/~afd/papers/2024/TOSEM.pdf)). A report against json-c's lenient default mode risks the same reception, which makes STRICT the right target for accept-invalid testing. Harrand et al. found that 20 Java libraries agree on **only 0.75% of ill-formed files**, and that only 6 handle a 64-bit float overflow without error ([arXiv 2104.14323](https://ar5iv.labs.arxiv.org/html/2104.14323)). JSONTestGen found 34 fastjson2 bugs using LLM-generated tests judged by a **cross-version differential** ([arXiv 2410.09414](https://arxiv.org/html/2410.09414v2)). That is the same oracle as the team's old-vs-new run over 0.18, 0.19 and master, which found no regressions.

No peer-reviewed study tests incremental JSON parsers or the accuracy of error offsets, so the best precedents are test harnesses. Go's `encoding/json/jsontext` fuzzes a resumable decoder through random 8-byte short reads against a whole-buffer decode, and it checks validity monotonicity across RFC option sets, but it explicitly does not compare error offsets ([Go fuzz_test.go](https://tip.golang.org/src/encoding/json/jsontext/fuzz_test.go)). tree-sitter fuzzes random edits and undo with incremental reparsing ([fuzz.rs](https://docs.rs/tree-sitter-cli/latest/src/tree_sitter_cli/fuzz.rs.html)). pFuzzer runs each candidate input with and without an appended character "because not all parsers perform an EOF check" ([pFuzzer](https://core.ac.uk/download/249327981.pdf)). json-c's own `TEST_PARSE_CHUNKSIZE` hook re-runs its basic tests in chunks ([197e372](https://github.com/json-c/json-c/commit/197e372)). The team's harnesses go beyond all of these. They cover every split point, bytewise feeding, 3-piece splits, wrapping, reuse, streams and termination modes, and they compare error offsets.

The literature also says what coverage-guided byte fuzzing structurally misses, and each gap maps to a remaining json-c direction. Resource bugs need resource feedback. SlowFuzz drove PHP's hash table to 20 collisions in 64 insertions, where coverage-guided fuzzing never got past 8 ([SlowFuzz](https://ar5iv.arxiv.org/html/1708.08437)), and PerfFuzz found hot spots 5 to 69 times hotter than SlowFuzz did ([PerfFuzz](https://wcventure.github.io/FuzzingPaper/Paper/ISSTA18_PerfFuzz.pdf)). json-c's CVE-2013-6371 was found by a person, not a fuzzer. Size thresholds above 2 GB, as in CVE-2020-12762 and yajl's CVE-2022-24795 ([Ubuntu](https://ubuntu.com/security/CVE-2022-24795)), are out of reach of any `-max_len`. Multi-byte comparisons need help: on cJSON, AFL never produced `true`, `false` or `null` ([pFuzzer](https://core.ac.uk/download/249327981.pdf)). Redqueen solves such comparisons but fails when the input is transformed before the comparison ([Redqueen](https://www.ndss-symposium.org/wp-content/uploads/2019/02/ndss2019_04A-2_Aschermann_paper.pdf)), and `\u` decoding and hash lookups are such transforms. IJON feeds program state into the fuzzer through one-line annotations ([IJON](https://cispa.de/en/research/publications/68621-ijon-exploring-deep-state-spaces-via-fuzzing)). The team's gcov run already takes every reachable non-OOM branch of `json_tokener_parse_ex`, so the remaining lever is feedback on parser state and resource use, not more edge coverage.

## Fourteen directions remain, led by error fidelity and resource oracles

The team's coverage now includes every streaming class in the table, plus everything this round closed. Flag monotonicity found 0 violations over about 39k corpus files, one-shot and bytewise. Escape equivalence compared raw UTF-8, `\uXXXX` and surrogate-pair spellings, in values and keys, one-shot, bytewise and at every 2-split, in about 3M checks. Its only failures were the known UTF-8-split issue that PR #1014 fixes, and a reset between surrogate halves gives U+FFFD as expected. Exact-size heap chunks with no terminating NUL ran clean under ASan for 1.18M calls, and MemorySanitizer ran clean over all corpora in seven feeding modes and six flag sets. The de_DE decimal-comma locale parsed correctly under both the uselocale and the setlocale-fallback builds, and an exhaustive number-alphabet chunk test confirmed that PR #1006 fixes the split-number bug. Together these close the research notes' top-ranked recommendations (the flag lattice, escape equivalence, MSan and locale invariance). The table ranks what is left by expected yield against cost.

**Error-code consistency (item 1)** ranks first because it has a known positive and costs almost nothing. The monotonicity check as run asks whether a stricter flag set's acceptance implies that the laxer set accepts the same value. It never compares error codes when both sets reject, and that is exactly where the UTF-8 epilogue acts. With VALIDATE_UTF8, `[\xc3` returns "invalid utf-8 string", while flags 0 return "unexpected character". The cause is that `PEEK_CHAR` validated the lead byte before the state machine rejected it, and the epilogue rewrites any non-continue error while a multibyte sequence is pending ([json_tokener.c#L285-L294](https://github.com/json-c/json-c/blob/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/json_tokener.c#L285-L294); [#L1389-L1406](https://github.com/json-c/json-c/blob/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/json_tokener.c#L1389-L1406)). PR #1014 keeps that rewrite. The relation to add: when both flag sets reject, the error code and offset must match, unless the stricter set's own check legitimately fires at an earlier byte, and a UTF-8 error is valid only when the consumed prefix actually fails Python's strict decoder. The same oracle also catches the EOF rewrite behind Finding 5, so it doubles as the regression net for the epilogue-level fix the team should propose.

**The resource oracles (items 2 and 3)** cover the class json-c's first CVE belonged to, which fuzzers cannot see. The default `lh_char_hash` is seeded from getrandom, /dev/urandom, RDRAND and finally the time ([ChangeLog](https://github.com/json-c/json-c/blob/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/ChangeLog)). The opt-in `JSON_C_STR_HASH_PERLLIKE` hash starts from a constant `hashval = 1` ([linkhash.c#L447-L456](https://github.com/json-c/json-c/blob/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/linkhash.c#L447-L456)), so any application that selects it through `json_global_set_string_hash()` ([linkhash.h](https://github.com/json-c/json-c/blob/master/linkhash.h)) is open to the CVE-2013-6371 attack again. Generating colliding keys offline and timing the parse will show whether the cost grows quadratically. Forcing every seed source to fail tests the time fallback, and parsing the corpus under both hashes should give identical trees and iteration order. Memory amplification is the other gap. Finding 7 measured memory for comments only, and `perf_chunk.c` measured time. Nobody has measured how many bytes json-c allocates per input byte for constructs where every value becomes a heap object, and applications need that bound to set input caps.

**OOM injection in more modes (item 4)** follows from the most recent ownership fix. e0a1735 added `json_object_put(obj)` on the shared error exit. That is correct only if `obj` is cleared on every successful transfer, and today only the array and object insertion sites clear it ([json_tokener.c#L1426-L1429](https://github.com/json-c/json-c/blob/d2ce61eb214e4dac14b76b10de32a1cb7186d7ad/json_tokener.c#L1426-L1429)). A path that reaches the exit with `obj` still set is most likely in split and stream modes, where a value completes across a call boundary, and the team's fault injection has not run in those modes.

**BOM handling and surrogate key collisions (items 5 and 6)** are interop decisions more than likely memory bugs, and both are cheap to settle. The epilogue mechanism predicts that `EF BB BF {}` under VALIDATE_UTF8 reports "invalid utf-8 string" for perfectly valid UTF-8, which would mislead anyone parsing a file saved with a BOM. json-c's U+FFFD policy for lone surrogates is defensible, and Bishop Fox recommends replacement over truncation ([Bishop Fox](https://bishopfox.com/blog/json-interoperability-vulnerabilities)). Replacement still makes distinct keys equal, though, which is the collision that became ujson's CVE-2022-31116. Each should end in either documented behaviour or a STRICT-mode rejection.

**The 32-bit build and upstreaming (items 7 and 8)** are about platforms and lasting protection rather than new oracles. CVE-2013-6370 and open PR #1008 are 32-bit specific, and yajl's CVE-2022-24795 bites mainly where `size_t` is 32 bits. OSS-Fuzz builds for i386 but runs only the single-call harness there. Upstreaming has the most leverage. The team's `json.dict` already contains `\u`, a surrogate pair, the comment delimiters and multibyte UTF-8, which are exactly the tokens the upstream dictionary lacks. A fuzz target that reads its flags, split points and NUL choice from the input would run the team's metamorphic oracle continuously on three engines and two architectures. It would also guard the number-state rebuild in #1006 and the new UTF-8 state that #1014 keeps across calls, both likely candidates for json-c's habit of needing a second fix.

Three covered areas have small residual checks. The escape-equivalence generator should be confirmed to include code points whose low 16 bits fall in D800–DFFF (U+1D800, U+2D800, U+10D800), the class PR #893 fixed, along with the short escapes (`\/`, and `\n` vs `\u000a`) and upper- vs lower-case hex. The number alphabet has no NaN token, so the RapidJSON shape (`NaN`, then `.2e2` in the next chunk) is untested. The `printbuf_memappend_fast` negative-size and overlap issue deserves a comment on [PR #1011](https://github.com/json-c/json-c/pull/1011), even though the tokener cannot reach it.

## Conclusion

The frontier has moved. Crossy shows that json-c's value semantics match the mainstream, and the team's runs show that its memory safety holds under every sanitizer tried. The defects that remain are in how json-c reports results (which error code, at which offset, under which flags) and in how much CPU and memory an input costs. Crash oracles and cross-parser differentials cannot see either. json-c's history also shows that bugs come back through incomplete fixes more reliably than through new code. CVE-2013-6370 returned as CVE-2020-12762, the 2020 `json_parse` fix returned as #929, and 99c14de patched call sites while leaving the epilogue in place.

The most durable contribution is therefore probably not another finding. It is root-level fixes for the epilogue and chunk-state families, submitted together with the team's oracles as OSS-Fuzz targets, so the next partial fix is caught within a day, as PR #633's overflow was, instead of resurfacing years later as a CVE.
