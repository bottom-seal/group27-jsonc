How does the gate judge a rewrite of json_tokener_parse_ex?

Long image

A

Answer

A rewrite passes only if it gives the original's answers to about 1 million questions, asked in more than 30 ways, and does not cheat. Four iterations raised the share of planted mistakes it catches from 82–88% to 87–96%.

  1. The path rules keep a rewrite PR to json-c/json_tokener.c, so main's own checker judges it.1
  2. Before anything is built, the anti-cheat check rejects code that looks at its surroundings, switches checks off or carries test answers.2
  3. The checker feeds the original and the rewrite 5,698 inputs in more than 30 ways and compares every answer.3
  4. On rewrite PRs, a fuzzer also tries inputs nobody wrote; what it finds becomes a permanent input.4

  1. Only json_tokener.c? ↗

    The paths job runs ci/check_paths.py. A rewrite PR may change nothing but json-c/json_tokener.c, so it cannot weaken the tests or the checker that judge it.

  2. Free of cheats? ↗

    oracle/cheats.py compares the rewrite with the original before building it. A cheat ends here as REJECTED (exit 5); the rewrite is never built or run.

  3. Build both versions ↗

    Both tokeners are compiled with cmake's exact command, with ASan and UBSan, and linked with the recorder and its allocation wrappers.

  4. Ask both 30+ ways ↗

    The original runs first; its time sets the rewrite's limit, 20 times as long and at least 10 seconds.

  5. Same answers? ↗

    oracle/compare.py matches every answer exactly. A difference is FAIL (exit 1); a crash, leak, sanitizer report or timeout is CRASH (exit 2).

  6. Can merge ↗

    Once branch protection is on, paths and gate must pass and a teammate must approve. It is not on yet.

A separate fuzz job fuzzes rewrite PRs for 5 minutes. It is not a required check, because a short run can miss things.5

One exception to exact matching

Answers given while an allocation fails on purpose are judged by what they say. A rewrite may allocate in another order, so its k-th allocation need not be the original's k-th. It may give any answer the original gave for that input under some failed allocation, report out of memory, or give the normal answer. A crash or leak still fails.

How much stronger did each iteration make it?

  • Iterations 1 and 2 did most of the work: new ways of asking, not more inputs. Iteration 4's 2,268 inputs caught only 3 more mutants.
  • The 9 mistakes planted by hand: 0 caught before, all 9 from iteration 2 (iteration 1 misses the one that is only slow on large inputs).
  • Mistakes that forget a value between calls: 0 of 9 caught before, 9 of 9 from iteration 1.
  • Leaving out mutants shown to be harmless, the last stage catches 95–100%. 94 survivors are unproven: fuzzing found no difference, but nobody proved them harmless.

What these numbers measured

The mutation runs used the scratch versions of each iteration. The committed iterations are clean rewrites of them and were not measured again. The failed-allocation rule came after the measurement and may catch fewer allocation mistakes. Its tests show the planted ones are still caught.

How does the anti-cheat check work?

It compares the rewrite with the original, so whatever the original does stays allowed. It reads three things: the list of functions the compiled code calls and defines (nm), the code after macros are expanded, and the raw text.2

RuleRejectsOnly this rule catches
R1 CallsFunctions a parser has no use for: the environment, files, the clock, printing, exiting, __real_malloc16 of 34 cheats
R2 DefinitionsNames the C library or the sanitizers own, such as malloc and __lsan_is_turned_off4
R3 Compiler tricksno_sanitize, constructor and optimize attributes, inline assembly, pragmas5
R4 Build detectionTests on __SANITIZE_ADDRESS__, FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION, __OPTIMIZE__4
R5 Copied inputsA new string of 4 or more characters that occurs in the gate's inputs1
Cheats tried
34 in 5 groups; 31 caught, only 1 by two rules
Honest refactors tried
11, all pass: helpers, macros, extra malloc, assert, snprintf, lookup tables
Mutants from the review
2,401 honest code changes, none rejected

What it cannot see

A test answer spelled as characters, compared byte by byte, or matched by a hash of the input contains no string R5 can find. The fuzzer is the defence: a rewrite that special-cases the gate's inputs is still wrong on new ones.

What does the fuzzer add?

  1. One program, two versions

    fuzz/fuzz.py compiles the original and the rewrite separately and renames every global symbol of each, so both link into one program.

  2. New inputs

    libFuzzer keeps changing inputs, starting from the gate's inputs and the bug hunt's 27,000-input corpus. Byte 0 picks the flags, byte 1 the cut point.

  3. Four ways each

    Both versions parse each input whole, cut in two, byte by byte and as several documents. Any difference stops the run with both answers.

  4. Finds become inputs

    It prints the input as a line for oracle/inputs/fuzz.txt. From then on the gate checks it on every run.

Run against the original itself, an earlier version of this harness found no difference in about 26 million inputs.4
